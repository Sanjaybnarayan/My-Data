# A File In A Downloads Folder Is Not A Record

Phase 3's remainder. `DocumentStore.capture` gains `generatedFrom`,
`js/modules/reports.js` files what it generates, `document.generatedFrom` in the
schema, and two more rows in the architecture document.

## What generating did

`domain/docxtemplate.js` reads a `.docx`, finds its fields and produces new
bytes — the whole of what Phase 3 asks for, built and merged. The screen then
did this with them:

```js
await download({ blobParts: [generate(template.parts, values)], … });
toast('Generated — your template is untouched');
```

Downloaded, and nothing else. Which means the application **could not say it had
produced anything**: no record, no idea which template it came from, no version
history, and nothing in the household's own Drive. The document existed only in
a downloads folder, where this application cannot see it, search it, or tell
anybody it exists.

`document.versionCount` was already read on the documents screen and already
maintained from Drive's own revisions. A generated file never reached any of
that.

## What it does now

Generating still downloads — a person asked for a file and gets one — and then
files the same bytes through `DocumentStore.capture`, the path a scanned
document takes. That is deliberate rather than convenient: it means a generated
document gets the same encryption at rest, the same upload queue, the same Drive
folder and the same revision-backed `versionCount`, with no second
implementation to drift.

## `generatedFrom`, and why it is a name rather than a reference

A generated document records the template it came from, by **file name**.

Not a `ref`: a template is a `.docx` the household uploads each time, and there
is no template record to point at. Naming the file is the whole of what can
honestly be recorded — and it is worth recording, because a generated document
that cannot say what it was generated from is one nobody can reproduce or check.

**It is absent for anything scanned.** Defaulting it to *"a scan"* would be a
claim about a file somebody pointed a camera at. A test asserts a captured PDF
comes back with nothing in that field, and the mutation that defaults it fails.

## The wiring had no test, and now it has a probe

Deleting the `capture` call from the reports screen changed **no test**. The
generated bytes would go on downloading, the toast would go on saying
*"Generated"*, and nothing in the repository would notice that filing had
stopped.

This is the second time in two tranches, so it went to the same place as the
first: `wired:js/modules/reports.js#documentStore` in the architecture document,
which fails with the row named when the call is removed. Verified by removing
it.

Two rows were added, not one. The other says the DOCX template engine exists at
all — `export:js/domain/docxtemplate.js#readTemplate` — because the roadmap
carried *"no DOCX template engine"* for two tranches after it was built, and a
probe is what stops that recurring.

## Typecheck fell ten, and the budget followed

`capture` had no `@param` types. Adding them — needed because destructuring
`generatedFrom` across a line break lost the inference the one-liner had —
resolved **ten** pre-existing findings across its callers. The budget is now
**171**, down from 181.

That is worth naming: the ten were not introduced by this tranche and were not
found by looking for them. They were sitting behind one untyped parameter list
on a method four screens call.

## What mutation testing found

Four mutations, all four caught:

| Mutation | Caught by |
| --- | --- |
| **`generatedFrom` is dropped on write** | *it is recorded, and says which template it came from* |
| **`generatedFrom` defaults to "a scan"** | *a scanned file says it came from nowhere, because it did* |
| **No blob is written** | six tests, including the document round-trip |
| **The reports screen stops filing** | the `wired:` probe, with the row named |

## What is still not built

**Word content controls and `MERGEFIELD` are done** — see
`docs/WORD_FIELDS.md`, written after this and in answer to the paragraph that
used to be here.

**PDF output.** The prompt asks for it; `reports/pdf.js` writes PDFs already, so
the missing piece is rendering a *filled template* to PDF rather than to DOCX,
which means laying out Word content this application currently only rewrites in
place. It is not a small piece and it is not started.

**Template versioning.** Each generation is a new document record. Successive
generations from one template are related only by `generatedFrom` carrying the
same name; nothing groups them, and Drive's revision count applies to a file
rather than to a template's history.
